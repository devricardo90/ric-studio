# Guarded Jira Write Integration Contract

## Purpose

This document defines the architecture and safety contract for a future guarded Jira write integration in RIC Studio.

The goal is to make any future real Jira write action narrow, explicit, auditable, and subordinate to the RIC protocol. Jira may support planning visibility and evidence capture, but it must not replace local evidence, Commit Gate, Push Gate, or Ricardo final validation.

This task is documentation-only. RIC-STUDIO-076A does not implement Jira writes, call Jira API, call Jira CLI, create credentials, store tokens, add dependencies, or modify the existing Jira dry-run tool.

## Relationship With RIC-STUDIO-075A Dry-Run

RIC-STUDIO-075A delivered a local dependency-free Jira dry-run interface.

The dry-run interface is the mandatory baseline for any future guarded write integration:

- Dry-run mode remains the default behavior.
- Real writes must not be introduced by changing the dry-run contract silently.
- Every future real write action must first be representable as an exact dry-run operation.
- The dry-run output must identify the intended Jira action, target issue or project, requested state, evidence references, and blocked conditions.
- DONE remains blocked in dry-run and must stay blocked for automation unless Ricardo final validation has already occurred and a future task explicitly approves a guarded post-validation write.

RIC-STUDIO-076A extends the architecture contract beyond dry-run. It does not change `tools/jira/dry-run.mjs`.

## Non-Goals

RIC-STUDIO-076A does not:

- Implement real Jira API integration.
- Call Jira API.
- Call Jira CLI.
- Create, read, store, or modify tokens.
- Create, read, store, or modify credentials.
- Add dependencies.
- Change package or lock files.
- Create GitHub Actions.
- Modify runtime, model, app, or UI files.
- Modify `tools/jira/dry-run.mjs`.
- Modify `tools/jira/README.md`.
- Automate commit.
- Automate push.
- Mark any task DONE.
- Open a follow-up READY task.

## Allowed Future Jira Write Actions

The following actions may be considered for future implementation only after a separate approved task:

- Create issue.
- Transition issue to READY.
- Transition issue to IN_PROGRESS.
- Transition issue to REVIEW.
- Add comment.
- Attach evidence summary.

These actions are not approved for execution by this document alone. A future implementation task must define the exact command/API boundary, input schema, approval flow, credential source, audit log format, failure behavior, and validation evidence before any real Jira write is allowed.

## Permanently Blocked Or Guarded Actions

The following actions are blocked or require strict guardrails:

- Automatic DONE is blocked. Jira DONE may only happen after Ricardo final validation.
- Hidden transition is blocked. Every transition must be printed and approved before execution.
- Credential creation or storage is blocked.
- Token creation or storage is blocked.
- Automatic commit is blocked.
- Automatic push is blocked.
- Changing Jira project configuration is blocked.
- Changing unrelated Jira issues is blocked.
- Bulk updates are blocked unless a future Discussion Gate approves a specific narrow batch contract.
- Retrying a write in a way that may duplicate an issue, comment, attachment, or transition is blocked.

## Credential Policy

Future implementation must follow this credential policy:

- No hardcoded credential.
- No credential generated by an agent.
- No credential stored in the repository.
- No token generated by an agent.
- No token stored in the repository.
- No credential or token printed in terminal output.
- No credential or token written into audit logs, evidence docs, or operational docs.
- No checked-in `.env` file for secrets.
- Future implementation may only read credentials from explicit environment variables.
- The required environment variable names must be documented before implementation.
- Missing credentials must return `BLOCKED`.
- Ambiguous credentials must return `BLOCKED`.
- Unsafe credential source must return `BLOCKED`.

Agents must not improvise credential prompts, invent token values, search the repository for secrets, or ask Jira to create credentials.

## Execution Modes

Future Jira integration must have explicit execution modes.

### Dry-Run Mode

Dry-run mode is the default.

Dry-run mode must:

- Perform no Jira write.
- Perform no network call unless a future read-only status check is separately approved.
- Print the exact intended Jira operation.
- Print the target issue or project.
- Print the requested transition or write payload.
- Print required approval.
- Print blocked conditions.
- State that no Jira write occurred.

### Explicit Real-Write Mode

Real-write mode is future scope only.

Real-write mode must:

- Be introduced only in a future approved implementation task.
- Require explicit user authorization for the exact issue, action, and target state.
- Require a fresh dry-run for the same operation.
- Refuse to execute if the dry-run evidence is stale, incomplete, or mismatched.
- Refuse to execute if the operation includes DONE without Ricardo final validation.
- Produce post-write evidence.

Real-write mode must never be the default.

## Required Pre-Write Gate

Before any future real Jira write, the integration must prove:

- Git status is clean, or the dirty state has a documented reason and is explicitly accepted for this Jira action.
- The exact intended Jira operation was printed first.
- The target Jira issue or project is confirmed.
- The requested action is one of the allowed future Jira write actions.
- The action does not include a DONE transition.
- Ricardo authorization exists for the exact action.
- The dry-run operation and real-write operation match.
- The task id, Jira issue key, current intended state, and target state are visible.
- Changed files, validation evidence, and operational state do not contradict the requested Jira action.
- Package, lockfile, token, credential, runtime/model, app/UI, and GitHub Action boundaries are intact unless a future task explicitly allows otherwise.

If any pre-write gate fails, the result must be `BLOCKED`.

## Required Post-Write Gate

After any future real Jira write, the integration must record:

- Raw command output or raw API result summary with secrets removed.
- Resulting Jira key, status, or comment evidence.
- Confirmation that no hidden extra operation occurred.
- Confirmation that no unrelated issue or project was changed.
- Confirmation that no token or credential was printed or stored.
- Confirmation that operational docs were updated when the Jira action affects RIC task state.
- Confirmation that Commit Gate, Push Gate, and Ricardo final validation were not bypassed.

If the integration cannot prove whether a write occurred, the result must be `BLOCKED` and require human review.

## Failure Behavior

Future Jira write integration must fail closed.

Failure rules:

- Missing evidence returns `BLOCKED`.
- Missing credential returns `BLOCKED`.
- Missing authorization returns `BLOCKED`.
- Unknown current Jira status returns `BLOCKED`.
- Mismatched dry-run and real-write operation returns `BLOCKED`.
- Unexpected Jira response returns `BLOCKED`.
- Any possible duplicate write risk returns `BLOCKED`.
- No retry loops that write repeatedly.
- No fallback to a different issue.
- No fallback to a different project.
- No credential prompt improvisation.
- No best-effort write when evidence is stale.
- No automatic recovery that changes Jira state.

Failure output must say what was blocked, why it was blocked, and whether external Jira state may have changed.

## Mapping To Protocolo Rick

Jira is a planning and visibility layer. It is not the source of delivery truth by itself.

The lifecycle mapping is:

- Jira planning: ideas and candidate tasks may be represented in Jira, but Discussion Gate decides whether a task can become READY.
- Task READY: a task becomes executable only after scope, allowed files, forbidden scope, and validation are documented.
- Local execution: implementation or documentation work happens locally under the approved scope.
- Review: completed local work stops for evidence review. Jira may receive comments or REVIEW transition only through guarded approval.
- Commit Gate: commit requires local evidence and approval. Jira status cannot authorize commit by itself.
- Push Gate: push requires clean post-commit evidence and approval. Jira status cannot authorize push by itself.
- Ricardo final validation: DONE requires Ricardo validation or explicit acceptance with caveat.
- Jira DONE: Jira may move to DONE only after Ricardo final validation and only through a future guarded action that proves the validation happened.

Commit, push, CI, local dry-run, Jira transition, or an agent statement cannot replace Ricardo final validation.

## Validation Checklist For Future Implementation

Any future implementation of guarded Jira writes must validate:

- Dry-run remains the default mode.
- Real-write mode is not reachable without an explicit flag or equivalent explicit mode.
- Real-write mode requires user authorization for the exact issue, action, and target state.
- Missing credential returns `BLOCKED`.
- Missing authorization returns `BLOCKED`.
- DONE transition returns `BLOCKED` unless Ricardo final validation evidence is present and a future task explicitly allows the guarded post-validation write.
- Create issue writes only the approved project and summary/body fields.
- READY transition targets only the approved issue.
- IN_PROGRESS transition targets only the approved issue.
- REVIEW transition targets only the approved issue.
- Add comment targets only the approved issue.
- Attach evidence summary targets only the approved issue.
- Unknown issue key returns `BLOCKED`.
- Unknown project returns `BLOCKED`.
- Mismatched dry-run and real-write operation returns `BLOCKED`.
- No token or credential appears in output.
- No token or credential appears in audit logs.
- No package or lockfile change is required.
- No GitHub Action is created.
- No commit or push is automated.
- Operational docs are updated when task state changes.
- `tools/jira/dry-run.mjs` behavior remains dependency-free and safe unless a future task explicitly approves a scoped change.

## RIC-STUDIO-076A Boundary

RIC-STUDIO-076A defines the guarded Jira write integration contract only.

It does not implement Jira writes, call Jira API, call Jira CLI, make network calls, create or read tokens, create or read credentials, add dependencies, modify package or lock files, modify `tools/jira/dry-run.mjs`, create GitHub Actions, change runtime/model/app/UI files, mark DONE, commit, or push.
